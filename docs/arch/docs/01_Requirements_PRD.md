**How to read this document**

- Every requirement has an ID. New or changed requirements are edited here, never in a separate file.
- **Src** column: **O** = stated by the product owner; **P** = proposed by the author to make the product complete, and needs the owner's confirmation.
- **TBD (Rxx)** means the value will be filled in from the research report `docs/research/Rxx_*.md`.
- "Shall" is mandatory, "should" is a goal that may be traded against cost.

## 1. Purpose

Build one hardware family — the Universal Controller (UC) — that can be configured for many industrial IoT applications, so the same boards can be sold to many customers with different needs. A customer pays only for the functions they need: someone who does not want LoRa does not pay for LoRa.

The UC acquires data over industrial protocols and from configurable IOs and analog inputs, and moves it over wired and wireless links (CAN, RS-485, Ethernet, Wi-Fi, BLE, LoRa, 4G LTE). Security and safety are non-negotiable. Low cost and easy manufacturing are key.

## 2. Product concept

The UC is a stackable family of individually enclosed modules, in the style of a stackable PLC. Modules click together side by side and share one common bus connector. Each module is also a product on its own: with its own power input it works standalone as a remote node.

| Unit | Role in a stacked gateway | Role standalone |
|---|---|---|
| **Fieldbus-controller module** (formerly the baseboard, then the IO controller; renamed by the owner 2026-11-16; optional) | When fitted, the preferred coordinator: hosts the IO image, holds the keys (PSA L3), routes data, orchestrates updates. | A small fieldbus / IO controller and data logger with RS-485, CAN-FD and optional Ethernet. |
| **4G + Ethernet + Wi-Fi module** | Cloud uplink over LTE, Ethernet or Wi-Fi. | A standalone 4G / Ethernet / Wi-Fi gateway or router-type node, running Zephyr or Linux. |
| **Wi-Fi + BLE module** | Low-cost wireless uplink and local BLE access for customers who do not need 4G. | A Wi-Fi / BLE remote node. |
| **LoRa module** | Collects data from remote LoRa nodes. | The remote LoRa node itself (the same hardware). |
| ~~Fieldbus module~~ | Removed by the owner on 2026-11-14. The baseboard keeps 1 × isolated RS-485 (FB-1). | — |

The same module hardware is used on the gateway side and on the node side. For example, the LoRa module in the gateway stack is the same part that sits in the field as a remote node; the same applies to the Wi-Fi + BLE module.

## 3. Target applications

The product shall serve a broad range of applications. The survey in R10 will rank them and fix the IO mix and the standard configurations (SKUs). Candidate applications being surveyed: energy monitoring and sub-metering, DG-set monitoring, solar plant monitoring, telecom tower monitoring, water and wastewater (pumps, level, flow, pressure), agriculture and irrigation, environmental and effluent data logging, cold chain, HVAC / BMS, machine monitoring, street lighting, EV charging, gas and oil RTUs, transformer monitoring, metering data concentrators, tank monitoring.

## 4. Requirements

### 4.1 System and modularity

| ID | Requirement | Src |
|---|---|---|
| SYS-1 | **No baseboard** (owner, 2026-11-16): the system is a set of standalone modules — Fieldbus controller, 4G modem card, Wi-Fi + BLE, LoRa — any of which may be used alone or stacked with any others; no module is mandatory and any can be left out without redesign. **Any combination shall work** (owner, 2026-11-16): each of the four modules — 4G, Fieldbus controller (incl. Ethernet), Wi-Fi + BLE, LoRa — shall work together with any of the other three, so the inter-module link cannot depend on one particular module (for example as USB host). | O |
| SYS-2 | Every module shall use the same bus connector with the same pin assignment. | O |
| SYS-3 | Every module shall also operate standalone, with its own power supply (see 4.8), as a remote node / slave of a gateway. | O |
| SYS-4 | Modules shall communicate with each other over a protocol available on every MCU used in the family (ST, NXP, Nordic, Espressif). **Physical layer (2026-11-16): half-duplex RS-485 on the two signal pins of the 4-pin bus (SYS-11)**, driven from a UART on each module through a non-isolated transceiver (THVD1410 / SP3485 class, ≈ INR 26 — ESTIMATE); proposed 2 Mbit/s, headroom to ≈ 4 Mbit/s (limit set by the ESP32-C6 and STM32WLE5 UARTs). I3C, CAN-FD and 10BASE-T1S were checked and rejected: I3C and an Ethernet MAC exist only on the STM32H5, the ESP32-C6 has classic CAN only and the STM32WLE5 has no CAN. Load ≈ 0.1 Mbit/s for the IO image; bulk 4G traffic uses the 4G card's own RJ45. | O |
| SYS-5 | Coordinator election (owner, 2026-11-16): in a stack, the most capable fitted module becomes the coordinator automatically — priority Fieldbus controller (STM32H5) > Wi-Fi + BLE (ESP32-C6) > LoRa (STM32WLE5). The coordinator hosts the shared IO image, the cloud session, peer authentication and update orchestration. Modules talk over the RS-485 stack bus (SYS-4) by publish–subscribe (SYS-12); the coordinator only hands out transmit turns (≈ 20 ms cycle), so only one module transmits at a time. | O |
| SYS-12 | **Publish–subscribe communication between modules** (owner, 2026-11-16). Each module publishes frames tagged with a topic in its transmit turn; every module hears every frame on the shared RS-485 pair and keeps the topics it subscribes to, so there is no relaying through a hub. Inside each Zephyr module the same model is used (zbus channels, selected channels bridged onto the bus); the coordinator maps bus topics to MQTT topics for the cloud. Latency ≤ one bus cycle (≈ 20 ms). Every frame carries a sequence number, CRC and a message authentication code with the stack key handed out by the coordinator (SEC-5); output commands are accepted only from the configured owner (IO-6). Frame format and topic list — in the specification. | O |
| SYS-6 | A module shall be upgradable later to a different chipset (for example ESP32-C6 replaced by an NXP or Nordic Wi-Fi + BLE equivalent) without changing the bus connector, the enclosure or the other modules. | O |
| SYS-7 | The coordinator shall detect which modules are fitted and identify their type and hardware revision: discovery by each MCU's unique ID (no address switches, no slot-order line, so the physical slot order is not known); each module's processor reports type, hardware revision (resistor straps), serial number (OTP) and firmware version over the stack bus. No ID EEPROM. | P |
| SYS-11 | One identical **4-pin** bus connector on every board (owner, 2026-11-16: "no need for the 40 pin connector now, just 4 pin connector is sufficient"): **BUS_V, GND, RS485_A, RS485_B**, on both side walls of every module, joined by a bridge plug; all four pins pass straight through, so modules can be stacked in any order. Power pins rated ≥ 3 A (full stack ≈ 1.7 A at 12 V, 2.2 A at 9 V). Dropped with the 40-pin bus: TOKEN slot order (SYS-7), IRQ_N (events wait for the next poll, ≤ ≈ 20 ms), per-slot PWR_EN (BASE-4), PFAIL_N (a bus message instead, PWR-2), SYNC (time sync by broadcast), GNSS pin (CELL-10) and SWD (programming via USB-C, MFG-2). Cost ≈ −INR 65 per module for the connector, +≈ 20 for the bus transceiver (ESTIMATE). | O |
| SYS-8 | The maximum number of modules in one stack shall be defined — proposed 5, TBD (R06, R07). | P |

| D-39 | **CSMA on the RS-485 stack bus (owner asked 2026-11-23: "how to add csma over rs485 for interchip communication").** Today (SYS-4 / SYS-5): the coordinator hands out transmit turns every ≈ 20 ms, so no collisions but up to one cycle of latency and a single point of control. Options: (a) **CAN-style arbitration on RS-485 (CSMA/CD + priority)** — drive DE from inverted TXD so a module drives the bus only for '0' bits; bias resistors (A pulled up, B pulled down, fail-safe receivers) make '1' recessive, so '0' wins like CAN; receivers stay enabled and each sender compares every byte it reads back, the lowest priority-ID wins without corrupting the frame and losers retry when the line is idle ≥ 11 bit times; costs one inverter (or a transceiver with this mode) and bias resistors per module, speed falls to ≈ 250 kbit/s–1 Mbit/s on the short stack (IO-image load ≈ 0.1 Mbit/s); works on every module UART (STM32, ESP32-C6, STM32WLE5); (b) **plain CSMA/CA** — listen for idle, random back-off, ACK and retry; no hardware change, but colliding frames are both lost, fine only at low load; (c) keep coordinator-polled turns. Frames keep sequence number, CRC and MAC (SYS-12) in every option. **Owner, 2026-11-23: "but the same rs485 will be used for external peripherals as well" — with standard external RS-485 devices (Modbus RTU and similar) on the same pair, (a) and (b) do not work: those devices drive '1' actively and do not listen before talking, 120 Ω terminations on long cables kill the recessive level, and Modbus RTU allows only one master; the shared bus would also run at the slowest device's baud rate (typically 9.6–115.2 kbit/s instead of ≈ 2 Mbit/s) and bring field-cable surges and ground loops into every module's non-isolated stack bus.** | Recommended: keep two buses as today — the internal stack bus between modules (CAN-style arbitration or coordinator turns) and the isolated field RS-485 port for external peripherals (Modbus RTU, coordinator as master).
